# NEXION v0.2.9 — 두 SQLite 파일·앵커 간 복구 장애 경계 검증

**2026-11-19 / 읽기 및 관찰 위주의 오프라인 Python 연구**

## 실험 목표와 범위

v0.2.8은 관리자 승인 및 복구 직전 점검을 구현했지만 실제 권한 DB와 철회 저널의 원자적 갱신을 보장하지 않습니다. 이번 단계는 **기존 코드에 복구 실행 명령을 추가하지 않고**, 철회 트랜잭션의 중단 시점과 재시작 시 안전 차단을 검증합니다.

`tests/test_recovery_crash_windows.py`는 `TemporaryDirectory` 안의 **실제 SQLite 권한 DB와 별도 저널 DB** 및 테스트 HMAC 앵커를 사용합니다. `mock.patch`로 예외를 의도적으로 발생시킵니다. 네트워크·외부 사용자 연락·실설비 연결 없이 재현됩니다.

## 장애 주입 매트릭스

| 중단 지점 | 재시작/진단 관측 | 확인할 안전 조건 |
|---|---|---|
| 시작 전 정상 데이터 | `CLEAN` | 이 판정은 **복구 승인**이 아님 |
| 철회 의도(intent) 기록 후, 권한 DB 변경 전 | `PENDING_UNCOMMITTED` | 일반 서비스 재시작/전송 거부; 리뷰 전용으로만 조사 가능 |
| 권한 DB에서 철회 확정 후, 저널 이벤트 추가 전 | `PENDING_COMMITTED` | 전송 차단, 검토 계획은 **비실행** |
| 저널 트랜잭션 안에서 예외 발생 | 롤백 뒤 `PENDING_COMMITTED` 유지 | 이벤트/헤드가 반쯤 기록되지 않음 |
| 저널 커밋 후, 별도 앵커 파일 기록 전 예외 | `UNTRUSTED` / 앵커 불일치 | 서비스 및 읽기 전용 저널 재오픈도 차단 |
| 저널과 앵커 기록 완료 | `CLEAN` | 철회된 개별 참여자에게는 메시지 전송 불가 |
| 의도 기록 없이 권한 DB를 변경한 비정상 순서 | `DIVERGED` | 서비스 재시작/전송 거부 |
| 정상 완료 직후 재시작 | `CLEAN` | 기존 철회 상태가 살아나지 않음 |
| 장애 조사 및 계획 수립 | `PENDING_COMMITTED` 유지 | 권한 DB·저널·앵커 변경 건수/내용 불변 |

## 검증 명령

```sh
cd nexion
python -m unittest discover -s tests -p 'test_recovery_crash_windows.py' -v
python -m unittest discover -s tests -q
```

이번 단계에서 기존 156개에 신규 **9개 테스트**를 더했습니다. 코드 변경은 새 테스트와 문서에만 적용되며 실행 API는 변경하지 않았습니다.

## 새롭게 확인된 복구 운영상의 제약

`finish_withdrawal()`은 저널 DB 커밋 뒤 별도 앵커 파일을 갱신합니다. 따라서 **저널 커밋과 앵커 갱신 사이에서 중단**되면 저널 이벤트는 내구적으로 기록됐으나 앵커가 이전 값인 상태가 가능합니다. 이때 `verify()`는 실패하여 차단합니다. `open_for_review()` 역시 인증 실패로 열리지 않으므로 현재의 승인 계획 경로만으로는 **자동으로 복구할 수 없습니다**. 이 동작은 잘못된 전송을 막지만 사람의 독립 증빙 확인을 필요로 하는 가용성 제약입니다. 앵커 자동 재생성으로 이를 우회하면 안 됩니다.

재시작 중 모든 노드에서 철회 정보가 최신임을 보장한다는 뜻은 아닙니다. 공유 권한 DB를 검사하는 단일 프로세스 시뮬레이션에 한정됩니다. `RecoveryAssessment.delivery_permitted`는 전체 데이터 정합성 검사 결과이고, 특정 참여자의 동의나 재참여 권한을 의미하지 않습니다.

## 다음 단계에 필요한 설계 (현재 **미구현**)

1. 권한 DB·저널·앵커의 commit ordering, 쓰기 잠금, crash-consistent 독립 신뢰 기준을 분리해 명세할 것. SQLite 다중 DB ATTACH나 WAL을 무조건 원자적이라고 가정하지 말 것.
2. 외부에 독립 보관된 서명/증빙 기반의 **읽기 전용 복구 증명 절차**를 먼저 설계할 것. 앵커 불일치시 임의 자동 재발급 금지.
3. 사용자 동의, 권한 DB 철회 상태, 독립 감사 검토를 모두 확인하기 전에는 쓰기/전송/재참여 권한을 부여하지 말 것.
4. 프로세스 예외 모의는 OS 강제 종료, 전원 손실, fsync 오류, 스토리지 손상과 같지 않음. 실제 내구성/원자성 보장 여부는 별도 검증 필요.

**안전 경계:** 이번 코드는 생산용 복구 기능, 실제 신원 검증, 합의 알고리즘, 복구 실행 권한을 제공하지 않습니다. 외부 시스템 접속, 장비 가동, 자동 구매도 없습니다.
