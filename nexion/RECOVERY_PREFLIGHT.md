# NEXION v0.2.8 — 복구 승인 직후 사전 점검과 경쟁 조건 장애 주입

**2026-11-18 · 오프라인 Python/SQLite 검증 단계**

## 목적

v0.2.7 복구 승인 상태 머신에는 마지막 확인 단계에서 예외가 나면 메모리 상태가 `APPROVED`로 남을 가능성이 있었습니다. 또한 승인된 작업지시서를 다시 조회하는 시점과 미래의 실제 데이터 수정 사이에 상태 변경이 발생할 수 있습니다.

이번 단계는 **복구 명령을 구현하지 않고**, 안전하게 실패하도록 다음 두 부분을 개선합니다.

1. `RecoveryReviewSession.approve()`에서 마지막 두 번의 유효성 검사를 모두 통과해야만 메모리 상태가 `APPROVED`로 전이됩니다. 두 번째 검사가 실패하면 계속 `REVIEWED`로 남고 작업지시서를 발급하지 않습니다.
2. `preflight_recovery()`는 유효한 승인 세션의 작업지시서와 권한 DB/철회 저널 스냅샷을 **두 차례 읽기 전용 재검증**합니다. 사이에 관측 가능한 데이터 변경이 발생하면 `RecoveryDenied`로 차단합니다.
3. 스냅샷 지문에 `audit` 테이블을 포함하여 **감사 기록만 변경되는 경우**에도 기존 승인이 무효가 됩니다.

## 실제 동작 범위

`preflight_recovery()`는 `RecoveryPreflight`를 반환합니다. 반환 객체의 `status`는 `PRECHECK_ONLY`이고 `execute_automatically`, `may_reactivate_participant`, `delivery_permitted`는 항상 `False`입니다. 객체는 승인 토큰이나 암호화 서명이 아니며 실행 메서드가 없습니다. DB 복구, 메시지 전달, 승인 영속화, 실설비 연결은 없습니다.

## 재현

```sh
cd nexion
python -m unittest discover -s tests -p 'test_recovery_preflight.py' -v
python -m unittest discover -s tests -q
```

장애 주입 테스트는 승인된 상태에서 메시지/권한/감사 기록 또는 저널 인증 앵커에 변화가 생길 때의 거부, 승인과 사전 점검 사이 상태 변경, 두 검사 사이 마지막 순간 데이터 변경, 만료, 재시작으로 승인이 유실된 경우를 검증합니다. 테스트 데이터는 임시 폴더와 `.invalid` 예제 주소만 사용합니다.

## 위협 모델과 남은 작업

- **두 번의 검사만으로 경쟁 조건이 제거되지는 않습니다.** 최종 검사 직후 다른 프로세스의 변경이 가능하며 별도 SQLite 파일 사이의 원자적 스냅샷이나 잠금을 제공하지 않습니다. 프로덕션용 복구의 실행 전 최종 검증은 쓰기 트랜잭션에 묶어야 합니다.
- 모든 운영자 레이블과 증빙 참조는 시뮬레이션 데이터로 신원 보증이 없습니다. 복구 후 서비스 재개 허가는 없습니다.
- `RecoveryPreflight` Python 객체를 공격자가 복제·변조할 수 있으므로 **그 자체를 인증된 실행 허가증으로 사용하면 안 됩니다.**
- 키와 권한 DB, 저널, 앵커를 함께 교체하거나 롤백하는 공격은 탐지 보장 대상이 아닙니다. 롤백 방지를 위한 독립 신뢰 앵커가 필요합니다.
- 재시작 시 승인 기록은 유실되며 자동 복구되지 않습니다(기본 거부).

**다음 연구:** SQLite 별도 파일에 걸친 원자적 변경·읽기 경계 모델과 취소/재시작 장애 주입 시나리오를 순수 오프라인으로 설계합니다. 실제 데이터를 수정하는 복구 API는 신원·증빙·승인·원자성 보장 이후 별도 검토합니다.
